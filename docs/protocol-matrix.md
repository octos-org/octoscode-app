## Disagreements with `docs/phase0/protocol-matrix.csv` (41 rows)

Every row where this matrix disagrees with the phase-0 heuristic is flagged in `notes`
(`DISAGREE …` for native status, `KIND phase0=…` for kind). 41 rows total: **37** native
status + **6** kind, with **2** rows (`turn/steer_dropped`, `session/orchestration`)
carrying both flags. The classes, with the reason the heuristic missed:

1. **Kind corrections (6).** Phase-0 left `kind = "?"` where a method is in *neither*
   registry list, and marked `session/open` as notification-only:
   - `config/capabilities/list` → `request` (name-only; in neither list).
   - `profile/local/create` → `request` (in `UI_PROTOCOL_COMMAND_METHODS` @1364).
   - `session/status/read` → `request` (name-only; superseded by
     `session/status.get` = `SESSION_STATUS_GET` @1224).
   - `turn/steer_dropped`, `session/orchestration` → `notification` (const+decode exist
     at 4231669 `:6698`/`:6720`/`:7049`/`:7089`; only *advertised-list* membership is
     added at `a6ea8505`).
   - `session/open` → `request+notification` (it is in **both** lists @1364 and @1440).

2. **Native status false negatives (37).** Phase-0's `native_files=0` where native really
   decodes and consumes the method. The heuristic searched for the `<Camel>Event` name;
   it missed notifications whose Rust variant name is irregular, and it never looked at
   the transport's `methods::X` table or the `apply_protocol` consumer. Examples fixed:
   `message/delta`, `turn/completed`, `approval/*`, `tool/*`, `progress/updated`,
   `task/updated`, `task/output/delta`, `context/*`, `session/open`, `file/attached`,
   `protocol/replay_lossy` — all now `handled` with `path:line`.

3. **Native status false positives (0)** and **web-count corrections (0).** The web
   `web_src` counts reconcile **exactly** with the verified extractor once the match is
   `\bCONST\b OR "literal"` (the phase0 script's `\bCONST\b|"literal"` intent). No web
   count needed correcting; the two apparent diffs (`profile/local/create`, `turn/start`)
   were an artifact of matching only the `CORE_UI_METHODS.` prefix, and disappear under
   the name-or-literal rule.

## What this doc does NOT claim

- It does not prove runtime behaviour — only that a production path *exists* and is
  reachable from the code. No live `octos serve` turn was started (per RULES.md).
- `native_src` line numbers are from the read-only `ref/OctoSense` clone at
  `apps/appcard/app`; the octos-core decode lines are from the pinned `4231669` blob.
- `params_type` / `result_type` are empty for methods with no `UiCommand`/`UiResult`
  variant and no matching `<Camel>Params`/`<Camel>Result` struct (75 methods — the
  notification family and the name-only requests). Wire params for those are inline
  `serde_json::Value`, not a named struct.
