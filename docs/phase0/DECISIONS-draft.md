## D2. Rust vs Octoscript boundary
| Surface | Owner | Why |
|---|---|---|
| Protocol client, reconnect, replay, session store | Rust (`octos-app-transport`, `octos-app-store`) | stateful, async |
| Timeline, streaming markdown, reasoning, tool cells | Rust/Makepad (reuses aichat) | streaming, high volume |
| Composer (queue/steer/interrupt, vim later) | Rust/Makepad | input state, keyboard |
| Approvals, user questions (inline in the thread) | Rust/Makepad | request/response flow tied to turns |
| Diff review side panel | Rust/Makepad | large, interactive |
| Sessions sidebar, workspace-create, resume, history | Rust/Makepad | navigation state |
| Plan/task cards, goal/loop summaries, fleet/peer status, review summary, settings pages | Octoscript AppCard (`app.md` + `lint.json` + validator) | declarative, data-driven, read-mostly |

Any action on a declarative card (pause a loop, approve) goes back through a Rust handler. The Octoscript UI
profile has no onPressed, state, or async.

## D4. Protocol parity gate. Evidence: `protocol-matrix.csv` (generated by `protocol-matrix.py`)
- The contract has 125 methods (71 requests, 49 notifications).
- Web non-test source uses **83**. Native (AppCard) covers **21** of them, so **62 are missing**.
- The native side covers: session open/list/hydrate, turn start/interrupt/started/completed, message/delta,
  tool started/progress/completed, approval requested/respond/decided/cancelled/auto_resolved, diff/preview/get,
  task output read/delta, task/updated, progress/updated.
- Missing by group: agents (8) · loops (8) · monitors (8) · goals (6) · task list/cancel/artifacts (5) · session
  delete/fork/rollback/btw/files/status (6) · permission profiles (2) · config/capabilities/list ·
  profile/local/create · review/start · thread/graph/get · turn/state/get · turn/steer_dropped · turn/error ·
  message/reasoning_delta · user_question requested/respond · context compaction/normalization (3) ·
  peer staged/closed · plan/updated · projection/envelope · launch/resolve · approval/scopes/list · warning.
- Heuristic caveat: native coverage matches `methods::CONST`, a string literal, or a `<CamelMethod>Event` type
  name. `protocol/replay_lossy` is probably a false negative (the native type is `ReplayLossyEvent`). Lanes
  confirm each row.
- **Gate:** every web-used method is covered natively **and** exercised by a test through the production client path.

## D6. octos-core revision pin (NEW, blocks Phase 1)
- The web client's contract pins octos `4231669…` (see `core-contract.ts` `CORE_UI_CONTRACT_SOURCE`).
- AppCard vendors octos at **deb433e9, a local WIP commit** (v2.0.3-rc.11-23). The web pin is not in that clone.
- The vendored core is missing `memory/{ingest,load,search}`.
- Proposal: pick one octos revision for both the native app and the live `octos serve` used in gates, at or above
  the web's pin. Rebase the WIP onto it **with its owner's consent** (it isn't ours). Until then, the parity matrix
  is measured against the web pin.
