## Applying it app-wide

The two Stage B cards **are** the dark token set: their kits declare `"theme": "light"`
(the generator's only value) but the token VALUES are the dark palette — autonomy-11 bg
`#1C1C1E`/`#2C2C2E` text `#FCFCFC`; autonomy-12 bg `#191C1F`/`#1D1F23`. "The same
components with the dark token set" therefore resolves to CARD SELECTION: dark mounts
autonomy-11/12, light mounts the same screens' light twins (conversation-03, setup-06 —
texts isomorphic row-for-row). `theme::card_for` implements it; `OCTOSCODE_THEME` seeds
the preference in lib.rs's mount arm and the probe.

**Disclosed boundaries:**
- **System resolves DARK.** The makepad fork exposes no OS-appearance API (searched
  `octoscript-makepad-fork/crates/` — no dark_mode/OsTheme/appearance hits). The
  resolution is deterministic and tested; the OS read itself is **unverified on
  platform** until the host surfaces an appearance event.
- **Per-component light kits keep rendering light** when a light capture lowers them;
  their dark kits land per-component later. Both dark screens are fixed chrome (RULES
  8.10 carve-out), lowered through the DESIGN branch exactly as Gate B rendered them.
- **The preference is module-internal (in-memory).** Web parity stores light/dark in
  browser localStorage; the app-side persisted store (`user_store.rs`) belongs to the
  appcard layer — outside this card's Files. A restart returns to system (documented).
